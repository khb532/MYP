# Part 1: 소켓의 정의와 역사

## 1.1 소켓이란 무엇인가?

**소켓(Socket)**은 네트워크 상에서 프로세스 간 통신(IPC, Inter-Process Communication)을 가능하게 하는 **통신 종단점(endpoint)**입니다.

### 종단점(Endpoint)의 의미

통신의 "끝점"을 의미합니다. 전화 통화를 예로 들면:
- 양쪽 전화기가 각각 종단점입니다
- 전화선(네트워크)을 통해 두 종단점이 연결됩니다
- 각 종단점에서 말하고(send) 듣습니다(receive)

네트워크 통신에서 소켓은 데이터를 보내고 받는 **"문"** 또는 **"창구"**와 같은 역할을 합니다.

### 소켓의 실체

소켓은 **물리적인 하드웨어가 아닙니다**. 소켓은:

1. **소프트웨어 추상화**: 운영체제가 제공하는 개념
2. **데이터 구조**: 메모리에 저장된 연결 정보
3. **파일 디스크립터**: Unix/Linux에서는 파일처럼 취급됨
4. **API 인터페이스**: 프로그래머가 사용하는 함수 집합

```
[애플리케이션]
       ↓ socket(), send(), recv() 등
[소켓 API] ← 추상화 계층 (복잡함을 숨김)
       ↓
[운영체제 네트워크 스택]
       ↓
[네트워크 하드웨어]
```

### 인터페이스로서의 소켓

소켓은 **응용 프로그램과 전송 계층 사이의 인터페이스**입니다.

**인터페이스가 필요한 이유:**
- 네트워크 프로토콜은 매우 복잡합니다 (TCP/IP 스택, 패킷 분할, 재전송, 흐름제어 등)
- 프로그래머가 이 모든 세부사항을 알 필요가 없습니다
- 간단한 함수 호출만으로 통신 가능합니다

**비유:**
- 자동차를 운전할 때 엔진의 내부 작동을 몰라도 됩니다
- 핸들, 페달, 기어만 조작하면 됩니다
- 소켓 API가 바로 이런 "조작 인터페이스"입니다

### 소켓 vs 파일

Unix/Linux에서는 "모든 것은 파일이다"라는 철학이 있습니다. 소켓도 파일처럼 취급됩니다:

```c
int fd = open("file.txt", O_RDONLY);  // 파일
int sockfd = socket(AF_INET, SOCK_STREAM, 0);  // 소켓

// 둘 다 같은 방식으로 사용
read(fd, buf, size);
read(sockfd, buf, size);

write(fd, buf, size);
write(sockfd, buf, size);

close(fd);
close(sockfd);
```

**차이점:**
- 파일: 디스크에 저장된 데이터
- 소켓: 네트워크를 통해 전송되는 데이터

## 1.2 역사적 배경

### 탄생 (1983년)

**장소:** UC Berkeley (캘리포니아 대학교 버클리)
**개발자:** Bill Joy와 연구팀
**프로젝트:** 4.2BSD Unix

**배경:**
- 1980년대 초, 인터넷이 막 태동하던 시기
- ARPANET에서 TCP/IP 프로토콜이 표준화됨
- 하지만 이를 사용할 수 있는 프로그래밍 인터페이스가 없었음

**문제 상황:**
```
시스템 A: 자체 네트워크 API 사용
시스템 B: 다른 네트워크 API 사용
시스템 C: 또 다른 API 사용
→ 프로그램 이식 불가능!
```

**BSD 소켓의 등장:**
- 통일된 API 제공
- TCP/IP를 쉽게 사용 가능
- 다양한 프로토콜 지원 가능한 확장 가능한 설계

### 표준화 과정

**1983년:** 4.2BSD에 처음 등장
**1986년:** 4.3BSD에서 개선
**1988년:** POSIX 표준화 작업 시작
**1990년대:** 모든 주요 Unix 시스템에 채택
**현재:** POSIX.1-2008 표준의 일부

### 영향과 의의

**1. 인터넷 발전의 촉매**
- 누구나 네트워크 프로그램을 쉽게 작성 가능
- 초기 인터넷 애플리케이션 (FTP, Telnet, HTTP 등) 개발 가능

**2. 사실상의 표준**
- Windows Winsock API도 BSD 소켓 기반
- 모든 프로그래밍 언어가 소켓 API 제공
- Java Socket, Python socket, Node.js net 모듈 등

**3. 생태계 형성**
- 웹 서버, 이메일 서버, 게임 서버 등 모두 소켓 기반
- 현대 인터넷의 기반 기술

## 1.3 소켓의 필요성

### 1. 네트워크 하드웨어의 복잡성 은닉

**문제:** 네트워크 하드웨어는 매우 복잡합니다.

**하드웨어 레벨에서 해야 할 일:**
- 네트워크 카드(NIC) 제어
- MAC 주소 처리
- 이더넷 프레임 구성
- 물리적 신호 전송
- 인터럽트 처리
- DMA(Direct Memory Access) 설정

**소켓을 사용하면:**
```c
// 이것만 하면 됩니다!
send(sockfd, "Hello", 5, 0);
```

**장점:**
- 하드웨어 세부사항을 몰라도 됨
- 네트워크 카드가 바뀌어도 코드 변경 불필요
- 운영체제가 모든 복잡한 일을 처리

### 2. 다양한 프로토콜에 대한 통일된 인터페이스

**문제:** 다양한 프로토콜마다 다른 API를 사용하면 혼란스럽습니다.

**소켓의 해결책:**
```c
// TCP 소켓
int tcp_sock = socket(AF_INET, SOCK_STREAM, 0);
send(tcp_sock, data, len, 0);
recv(tcp_sock, buf, len, 0);

// UDP 소켓
int udp_sock = socket(AF_INET, SOCK_DGRAM, 0);
sendto(udp_sock, data, len, 0, ...);
recvfrom(udp_sock, buf, len, 0, ...);

// 비슷한 API, 일관된 패턴
```

**지원하는 프로토콜:**
- TCP (연결 지향, 신뢰성)
- UDP (비연결, 빠름)
- Raw IP (직접 제어)
- Unix Domain Socket (로컬 통신)
- SCTP, 블루투스 등

### 3. 운영체제 수준의 자원 관리 및 보안

**자원 관리:**

**포트 관리:**
```c
// 두 프로그램이 같은 포트 사용 시도
bind(sock1, ..., 8080);  // 성공
bind(sock2, ..., 8080);  // 실패: Address already in use
```

**버퍼 관리:**
- 송신 버퍼: 보낼 데이터 임시 저장
- 수신 버퍼: 받은 데이터 임시 저장
- 운영체제가 자동으로 관리

**흐름 제어:**
- 수신자가 느리면 송신 속도 자동 조절
- 버퍼 오버플로우 방지

**보안:**

**권한 관리:**
```c
// 1024번 이하 포트는 root만 사용 가능
bind(sockfd, ..., 80);  // 일반 사용자: Permission denied
                        // root 사용자: 성공
```

**이유:**
- 중요한 서비스 포트를 일반 사용자가 가로채는 것 방지
- 예: 악의적 사용자가 가짜 HTTP 서버(80번 포트)를 실행하는 것 방지

### 4. 이식성(Portability) 향상

**문제:** 플랫폼마다 다른 네트워크 API

**소켓의 해결:**
```c
// 같은 코드가 여러 플랫폼에서 동작
int sockfd = socket(AF_INET, SOCK_STREAM, 0);
// Linux ✓
// macOS ✓
// FreeBSD ✓
// Solaris ✓
// Windows (약간의 수정) ✓
```

**실제 예:**
- Apache 웹 서버: 수십 개 플랫폼 지원
- Redis: 크로스 플랫폼 데이터베이스
- 대부분의 네트워크 프로그램

### 5. 추상화를 통한 생산성 향상

**소켓이 없다면:**
```c
// 가상의 저수준 코드 (실제로는 더 복잡)
setup_network_card();
allocate_packet_buffer();
fill_ethernet_header();
fill_ip_header();
fill_tcp_header();
calculate_checksums();
fragment_if_needed();
send_to_network_card();
wait_for_ack();
handle_retransmission();
// ... 수백 줄의 코드
```

**소켓 사용:**
```c
send(sockfd, "Hello", 5, 0);  // 끝!
```

**생산성:**
- 개발 시간 단축
- 버그 감소
- 유지보수 용이

## 1.4 소켓의 작동 원리 (개념적 이해)

### 계층 구조

```
┌─────────────────────────────┐
│   애플리케이션 (웹 브라우저)    │
├─────────────────────────────┤
│   소켓 API (추상화 계층)       │ ← 프로그래머는 여기만 사용
├─────────────────────────────┤
│   전송 계층 (TCP/UDP)         │
├─────────────────────────────┤
│   네트워크 계층 (IP)          │
├─────────────────────────────┤
│   링크 계층 (이더넷)          │
├─────────────────────────────┤
│   물리 계층 (케이블, WiFi)    │
└─────────────────────────────┘
```

### 데이터 흐름

**송신:**
```
애플리케이션: send("Hello")
      ↓
소켓: 데이터를 송신 버퍼에 복사
      ↓
TCP: 패킷으로 분할, 헤더 추가
      ↓
IP: IP 헤더 추가, 라우팅
      ↓
이더넷: 프레임으로 캡슐화
      ↓
네트워크로 전송
```

**수신 (반대 순서):**
```
네트워크에서 수신
      ↓
이더넷: 프레임 디캡슐화
      ↓
IP: IP 헤더 처리
      ↓
TCP: 재조립, 순서 정렬
      ↓
소켓: 수신 버퍼에 저장
      ↓
애플리케이션: recv(buf) → "Hello"
```

### 소켓의 상태

소켓은 생명주기 동안 여러 상태를 거칩니다:

```
생성 (socket())
  ↓
바인딩 (bind()) - 서버만
  ↓
리스닝 (listen()) - 서버만
  ↓
연결 (connect() 또는 accept())
  ↓
데이터 송수신 (send()/recv())
  ↓
종료 (close())
```

## 1.5 소켓 프로그래밍의 범위

### 할 수 있는 것

**1. 클라이언트-서버 애플리케이션**
- 웹 서버/클라이언트
- 이메일 서버/클라이언트
- 채팅 프로그램
- 게임 서버

**2. P2P 애플리케이션**
- 파일 공유
- 비디오 채팅
- 블록체인

**3. 네트워크 도구**
- ping, traceroute
- 패킷 스니퍼
- 포트 스캐너

**4. IoT 통신**
- 센서 데이터 전송
- 원격 제어

### 할 수 없는 것 (직접적으로는)

**1. 라우팅 제어**
- 패킷이 어떤 경로로 갈지는 라우터가 결정
- 소켓은 목적지만 지정

**2. 물리적 연결 관리**
- WiFi 연결/해제
- 이더넷 케이블 인식
- 이런 것은 OS가 담당

**3. 프로토콜 설계 변경**
- TCP/IP의 동작 방식은 표준으로 정해짐
- Raw 소켓으로 일부 제어 가능하지만 제한적
